# Burwah Management

تطبيق إداري لمتابعة وإدارة العمليات التي تتم في تطبيق برواح. يختلف ما يظهر
للمستخدم حسب دوره وصلاحياته. هذا الدليل يركز على دور **المشرف المالي**، ويفصل
بين رحلة العمل المطلوبة وبين الأجزاء الموجودة حاليًا في الكود.

## خريطة المشروع

```text
lib/
  app/                           تجميع التطبيق والتنقل بين الميزات
    app.dart                     MaterialApp، الحالة العامة، وتدفق الدخول والخروج
    navigation/
      finance_tabs_shell.dart    تركيب تبويبات الواجهة المالية
  core/                          خدمات وأدوات مشتركة لا تخص ميزة بعينها
    constants/                   الألوان والنصوص والأنماط العامة
    di/                           تركيب الاعتماديات واختيار تنفيذ البيانات
    errors/                      أنواع الأخطاء والإخفاقات
    network/                     أساس الاتصال بالشبكة
    theme/                       سمة التطبيق
    utils/                       اللغة وتنسيق العملة
    widgets/                     عناصر واجهة مشتركة
  features/
    auth/                         الدخول والمستخدم والدور
      domain/                    الكيانات والعقود وحالات الاستخدام
      presentation/              شاشة الدخول وAuthCubit
    finance/                      عمل المشرف المالي
      data/                      مصادر البيانات والنماذج وتنفيذ المستودعات
      domain/                    كيانات المالية وعقودها وحالات استخدامها
      presentation/              الشاشات وCubits وعناصر الواجهة
  l10n/                           كل ملفات الترجمة
    app_ar.arb                    مصدر النصوص العربية
    app_en.arb                    مصدر النصوص الإنجليزية
    app_localizations*.dart       ملفات مولدة؛ لا تعدلها يدويًا
  main.dart                       بدء التشغيل وتحميل الإعدادات والاعتماديات
test/                             اختبارات الوحدات والواجهات
```

## أدوار التطبيق

التطبيق الإداري واجهة واحدة بأدوار متعددة. يحدد الدور الشاشات والعمليات
المسموح بها. النطاق الجاري تطويره هو **المشرف المالي**؛ ومن الأدوار التي تتعامل
مع دورة الموافقات الإدارة/الأدمن ورئيس المشرفين.

### رحلة المشرف المالي

#### الرئيسية

تجمع ملخصات السيولة والطلبات المعلقة والأرصدة والمحافظ التشغيلية. كل بطاقة أو
قسم يقود إلى تفاصيله:

- **الحسابات البنكية الرسمية:** عرض الحسابات والأرصدة والآيبانات، إضافة حساب،
  وتصدير البيانات إلى PDF. تعديل حساب قائم ينشئ طلب تعديل يذهب إلى الأدمن
  للموافقة أو الرفض، ولا يغير بيانات الحساب المعتمدة مباشرة.
- **طلبات سحب التجار والمستخدمين، وطلبات سحب المشرفين ومقدمي الخدمة:** مراجعة
  بيانات الطلب، ثم اعتماد وإرسال الطلب إلى الإدارة للقرار أو تجميده.
- **الاشتراكات والترقيات:** مراجعة الطلب والإيصال وبيانات التحويل. الإجراءات:
  اعتماد وإرسال للإدارة، تجميد مؤقت، أو رفض مع تسجيل السبب وإرساله إلى رئيس
  المشرفين للمراجعة.
- **المصاريف والمدفوعات:** إدخال المبلغ، اختيار حساب الصرف من الحسابات البنكية
  الرسمية، كتابة السبب، وإرفاق مستند اختياري. يرسل الطلب إلى الأدمن للموافقة
  أو الرفض.
- **الأرصدة المعلقة والتدقيق الرقابي:** فحص الطلبات المجمدة وتعارضات الآيبان
  ومشاكل الصرف. يمكن طلب فك التجميد وإعادة الإرسال إلى الإدارة، أو رفض الطلب
  ومصادرة المبلغ مع تسجيل السبب. التنفيذ الحالي تجريبي داخل الذاكرة: فك التجميد
  يعيد الطلب إلى الانتظار، والرفض يحفظ السبب ويستبعده من القائمة، دون تغيير أرصدة
  الحسابات البنكية؛ ربط قرارات الإدارة والـ API سيأتي لاحقًا.
- **محافظ الأقسام التشغيلية:** عرض الرقابة والحسابات والحركات حسب القسم، مع
  الإجمالي المتاح للسحب والرصيد المعلق. سجل العمليات يعرض إيداعات وسحوبات
  المستخدمين.

#### تبويبات أسفل التطبيق

- **المطابقة:** مراجعة طلبات ربط الحساب. يسجل النموذج التجريبي الاعتماد كطلب
  بانتظار مصادقة الإدارة، أو طلب شهادة آيبان حديثة، أو تجميد الطلب، أو رفضه مع
  حفظ السبب. تُزال الطلبات التي اتُخذ إجراء بشأنها من قائمة المراجعة النشطة.
  هذه الحالات محفوظة في الذاكرة حاليًا؛ لم يُربط إشعار المستخدم أو قرار الإدارة
  النهائي بالـ API بعد.
- **التسويات:** عرض رصيد الضمان والبنك المرتبط والرصيد المعلق، إنشاء طلب تسوية،
  مراجعة طلبات المستخدمين (استرداد كامل أو عمولة أو تسوية جزئية)، ومراجعة أحدث
  التسويات التي اعتمدها الأدمن. صفحة عرض تفاصيل التسوية ما زالت ضمن الشاشات
  المطلوب استكمالها.
- **العمولات:** متابعة دخل التطبيق الفعلي من العمولات وإحصاءاته.
- **التدقيق:** مراجعة سجل الإجراءات والحركات المالية.
- **الرئيسية:** ملخص الأعمال والانتقال إلى بقية الأقسام.

#### الملف الشخصي

يعرض بيانات المشرف المالي ومحفظته ورصيده المتاح والمعلق، ويتيح:

- إدارة مصفوفة الرسوم والعمولات المطبقة على عمليات التطبيق.
- تصدير كشف المدفوعات والإيرادات التفصيلي.
- مراجعة سجل تحركات المشرف داخل التطبيق.
- طلب سحب الأرباح إلى المالك، مع إرسال الطلب إلى الأدمن.
- تعديل معلومات السحب.

## دورة الموافقات المقصودة

المشرف المالي يراجع ويجهز طلبًا، لكنه لا ينفذ التحويل أو يغير السجل المعتمد
مباشرة. التدفق المعتاد:

```text
مستخدم / قسم
    -> طلب مالي أو مستند
    -> مراجعة المشرف المالي
    -> اعتماد وإرسال / تجميد / رفض مع سبب
    -> قرار الأدمن أو الإدارة
    -> تحديث الحالة والسجل وإبلاغ الأطراف المعنية
```

رفض طلب اشتراك له مسار إضافي لمراجعة رئيس المشرفين. ويجب حفظ كل قرار أو تغيير
في سجل تدقيق يحدد الفاعل والوقت والطلب والقيمة السابقة والجديدة وسبب الإجراء
عند انطباقه.

## Clean Architecture واتجاه البيانات

كل ميزة تملك طبقاتها؛ الاعتمادات تتجه إلى الداخل:

```text
Presentation -> Domain <- Data
                     ^
              app/core DI يركّب التنفيذ
```

- **Presentation:** الشاشات والـwidgets وCubit/Bloc. تستدعي حالات الاستخدام
  وتعرض النتائج، ولا تنفذ الاتصال بمصدر البيانات.
- **Domain:** كيانات العمل، واجهات المستودعات، وحالات الاستخدام. لا يعتمد على
  Flutter أو طبقتي العرض والبيانات.
- **Data:** مصادر البيانات والنماذج وتنفيذ واجهات المستودعات. تحول البيانات
  القادمة من المصدر إلى كيانات المجال.
- **app:** يجمع التطبيق ويدير التنقل بين الميزات. لا يضع قواعد العمل.
- **core/di:** نقطة تركيب الاعتماديات؛ تختار تنفيذ المستودع ومصدر البيانات.

### مثال: تحميل الحسابات البنكية

```text
BankAccountsScreen
  -> BankAccountsCubit
  -> GetBankAccountsUseCase
  -> FinanceRepository (domain contract)
  <- FinanceRepositoryImpl (data implementation)
  -> FinanceRemoteDataSource
  -> BankAccountModel / domain entities
```

التسجيل الحالي موجود في `lib/core/di/injection_container.dart`. المصدر المختار
حاليًا تجريبي (`FinanceMockDataSource`) وليس خدمة API فعلية.

### طلبات تعديل الحساب البنكي

ينشئ تعديل حساب بنكي قائم طلبًا منفصلًا بحالة انتظار، يحتوي القيم المعتمدة
والقيم المقترحة، ولا يغيّر الحساب المعتمد مباشرة. يحتفظ المصدر التجريبي
بالطلبات في الذاكرة فقط، لذلك لا تبقى بعد إغلاق التطبيق. واجهة قرار الأدمن
والتخزين الدائم عبر API ما زالا بحاجة إلى التنفيذ.

### طلبات المصروفات

يسجل طلب المصروف المبلغ والحساب المختار والسبب وحالة انتظار موافقة الإدارة،
ولا يخصم من رصيد الحساب عند الإرسال. يحتفظ الـMock بسجل الطلبات في الذاكرة فقط.
حقل المستند الحالي يحفظ اسم ملف تجريبي اختياريًا ولا يرفع محتوى صورة؛ اختيار
ملف فعلي ورفعه سيكونان ضمن تكامل التخزين والـAPI.

```text
ExpensesManagementScreen
  -> ExpenseRequestsCubit
  -> SubmitExpenseRequestUseCase
  -> FinanceRepository
  -> FinanceRemoteDataSource / FinanceMockDataSource
```

## الترجمة

جميع ملفات الترجمة موجودة في مجلد واحد هو `lib/l10n`. عدّل ملفات `.arb` ثم
ولّد ملفات Dart:

```sh
flutter gen-l10n
```

لا تعدل `app_localizations.dart` أو ملفات اللغات المولدة يدويًا.

## الحالة الحالية وما يحتاج ربطًا فعليًا

الكود الحالي نموذج واجهة أولي للمشرف المالي، وليس بعد تطبيقًا متصلًا بالكامل
بالخدمات الإدارية:

- تسجيل الدخول تجريبي ومحلي؛ اختيار المستخدم والدور ليس تحققًا من خادم.
- مصدر بيانات المالية المسجل هو Mock. يجب ربط API ومصدر حقيقي قبل الاعتماد على
  أرصدة أو طلبات فعلية.
- الأدوار الأخرى، واجهات الأدمن ورئيس المشرفين، قرارات الموافقة/الرفض، وإشعارات
  الأطراف الأخرى تحتاج تنفيذًا وربطًا.
- بيانات بعض الشاشات ثابتة للتوضيح. يجب أن تأتي الطلبات والحركات والأرصدة
  والموافقات من مصدر موثوق عند التكامل.
- يجب تطبيق صلاحية الدور في الخادم أيضًا، لا بالاكتفاء بإخفاء عناصر الواجهة.
